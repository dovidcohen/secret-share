Share secrets from the terminal

The shareasecret CLI speaks the same protocol as this site — same codes, same crypto, same read-once guarantee. Send from the terminal and receive in a browser, or the other way around. Requires Node 20+; nothing else to install.

Quick start

  1. Send — the secret is read from stdin and encrypted before anything leaves your machine: 
    cat id_ed25519 | npx shareasecret send --ttl 2h
    You get a share code like XKQ2-M7PT-tiger-ocean-cable-ruby-drum and a link. Speak the code over a call or send the link over any channel.
  2. Receive — with the code or the full link; the secret is written to stdout: 
    npx shareasecret receive XKQ2-M7PT-tiger-ocean-cable-ruby-drum > id_ed25519
  3. Sent the wrong thing? Burn it before anyone reads it: 
    npx shareasecret revoke XKQ2-M7PT-tiger-ocean-cable-ruby-drum

Sending

  • Anything on stdin works — pipe a file (cat .env | npx shareasecret send), a command's output (op read "op://vault/item/field" | npx shareasecret send), or run it bare and paste interactively (finish with Ctrl+D; Ctrl+Z then Enter on Windows). Text or binary, up to 10 KB.
  • --ttl sets the expiry: 90s, 30m, 2h, 1d — minimum 60 seconds, maximum 7 days, default 1 day. The drop is destroyed at first read regardless.
  • Pipes stay clean — the bare code goes to stdout and everything decorative goes to stderr, so CODE=$(cat key.pem | npx shareasecret send) captures just the code.
  • --json emits {"code", "link", "expiresAt", "ttlSeconds"} on a single line for scripts.

Receiving

  • Accepts the dashed code, the words separated by spaces, or the full https://shareasecret.io/r#… link. Case and lookalike characters (O/0, l/1) are forgiven.
  • The raw secret bytes go to stdout — redirect to a file for keys (> id_ed25519) and remember to chmod 600 it.
  • Reading claims the secret: the server copy is destroyed in the same transaction. A second attempt gets "already read" — if you didn't read it twice, treat that as a signal someone else did.

Scripting

Exit codes are stable, so automation can branch on what happened:

CodeMeaning
0Success
1Network or unexpected error
2Usage error (bad flag, malformed code, empty stdin)
3Wrong code words — the error reports attempts left before the drop burns
4No drop at that code (expired, revoked, or never existed)
5Already read or burned
6Secret exceeds 10 KB

A typical handoff: generate a credential, send it, and post the code — never the credential — to the channel where your teammate is waiting: 

TOKEN=$(create-scoped-token --expires 7d)
CODE=$(printf '%s' "$TOKEN" | npx shareasecret send --ttl 2h)
echo "Your token: shareasecret.io/r#$CODE (single read, dead in 2h)"

What the CLI does and doesn't do

  • Same security model as the web app. The five code words never leave your machine; the key is derived locally with Argon2id and the server stores only ciphertext and hashed tags. Sender and receiver can each use whichever interface they prefer.
  • It always uses the encrypted drop. The browser's direct-transfer-only mode (nothing stored, both parties live) is not in the CLI yet — if you need the never-stored guarantee, use the web app's checkbox for now.
  • Pin the version for the strongest posture. A web page is re-fetched every visit; a pinned package is not: npx shareasecret@0.1.1 send runs bit-identical, inspectable code every time. Install it permanently with npm install -g shareasecret.

No terminal on the other end? The code you send works right here in the browser too.
